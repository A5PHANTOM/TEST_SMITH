1. WHAT IS TESTSMITH?
────────────────────────────────────────────────────────────

  TestSmith scans any codebase, runs its existing tests, and produces a
  structured diagnostic report that identifies coverage gaps, dependency
  issues, and testability concerns. It is a read-only diagnostic tool —
  it NEVER writes test files or modifies your code.

  Stack:
    Backend : FastAPI (async) + SQLAlchemy + SQLite
    Frontend: React 19 + Vite 6 + Tailwind CSS 4
    Tests   : pytest + httpx (10 tests)

────────────────────────────────────────────────────────────
2. ARCHITECTURE (3 Agents + Orchestrator)
────────────────────────────────────────────────────────────

  +----------+     +----------+     +----------+
  | SCANNER  | --> |  RUNNER  | --> | ANALYZER |
  +----------+     +----------+     +----------+
       |                |                |
       v                v                v
   walks repo       runs tests      AST analysis
   finds files      parses output   markdown report

  Agent       What it does
  ───────     ─────────────────────────────────────────────
  Scanner     Walks the repository, finds source & test files by
              extension (.py, .js, .jsx, .ts, .tsx, .go, .rs,
              .java, .rb, .php). Detects project type (Python/Node).

  Runner      Copies repo to a temp sandbox, installs dependencies
              (pip install / npm install), runs pytest or vitest,
              and parses output for pass/fail/error/skip counts.

  Analyzer    Parses Python source files via AST to extract
              functions, classes, imports. Detects testability
              concerns (network calls, file I/O). Generates a
              markdown diagnostic report with 5 sections.

  Orchestrator (loop.py) runs them sequentially and streams
  real-time status updates via WebSocket to the frontend.

────────────────────────────────────────────────────────────
3. HOW IT WORKS (End-to-End Flow)
────────────────────────────────────────────────────────────

  1. User submits a local repo path OR a GitHub URL
     (e.g. https://github.com/user/repo.git)
  2. If GitHub URL: shallow clone (--depth=1) to temp directory
  3. Path validated against REPO_ROOT_WHITELIST
  4. Scanner walks the repo -> produces analysis.json
  5. Runner copies to sandbox, installs deps, runs tests
  6. Analyzer reads source files, runs AST analysis
  7. Final markdown report stored in the database
  8. All events stream in real-time via WebSocket to the browser

  Status lifecycle: pending -> cloning -> scanning -> running
                    -> analyzing -> done
                                    -> dismissed (user action)

4. QUICK SETUP
────────────────────────────────────────────────────────────

  Prerequisites: Python 3.12+, Node.js 20+

  Backend:
    cd backend
    python3 -m venv venv && source venv/bin/activate
    pip install -r requirements.txt
    cp .env.example .env   (or create .env with your settings)
    uvicorn app.main:app --reload --port 8001

  Frontend:
    cd frontend
    npm install
    npm run dev

  Open http://localhost:5173 in your browser.

6. API ENDPOINTS
────────────────────────────────────────────────────────────

  REST (all under /api)

  Method  Path                          Description
  ──────  ────────────────────────────  ─────────────────────
  GET     /health                       Health check
  POST    /runs                         Create a new run
  GET     /runs                         List all past runs
  GET     /runs/{id}                    Get run details
  POST    /runs/{id}/dismiss            Dismiss + cleanup

  Create Run request body:
    {"repo_path": "/local/path"}  or  {"repo_url": "https://..."}

  List Runs response:
    [{id, repo_path, repo_url, status, created_at, updated_at}]

  Get Run response includes all fields:
    analysis, execution_results, report (markdown)

  WebSocket

  Path:    /ws/runs/{run_id}
  Events (server -> client):

    agent_status  → {agent, status, detail}
    test_result   → {pass_count, fail_count, error_count, skip}
    report_ready  → {report: '...markdown...'}
    run_complete  → {run_id}
    error         → {detail}

9. SAFETY & ARCHITECTURAL RULES
────────────────────────────────────────────────────────────

  Non-Negotiable Rules:
  • Scanner reports only what is observed — no guessing
  • Analyzer produces reports from actual AST analysis — no invented findings
  • No test files are generated or written to disk — diagnostic-only
  • Report writing only through the API — never writes to the target repo
  • Prompt templates in prompts/ directory — never inlined in code

  Safety Measures:
  • Repo path validated against whitelist — rejects path traversal (../)
  • Source file reads capped at 100KB
  • AST analysis is read-only — never modifies files
  • Git clone uses --depth=1 (shallow, fast)
  • Test sandbox cleaned up automatically (shutil.rmtree)
  • .env gitignored — secrets never committed
  • Cloned repos cleaned up on dismiss/reject
